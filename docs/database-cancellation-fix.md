# SQLite 取消与连接池收尾修复

## 历史与遗漏

已核对 Codex 中的三次相关记录：

- `Fix SQLite rollback cancellation`：移除共享会话层重复 close，记录明确说明未运行测试。
- `修复插件 SQLite 重置异常`：插件内增加 rollback/close 的取消保护，未运行测试。
- `修复插件数据库重置异常`：推送同一笔 `028cf3a` 修复，未运行测试。

仅保护 rollback/close 仍有遗漏：自动或手动 commit 归还连接时也执行 pool reset；
SQL 执行中取消还可能进入连接失效/终止流程。`asyncio.shield()` 只保护子任务免受等待方
取消，无法阻止全局 `all_tasks()` 清扫直接取消子任务本身。

## 当前实现

1. `kernel/concurrency/cleanup.py` 统一登记受保护操作、等待者关系和全局清扫规则。
   重复取消只延迟调用方退出，操作结果及真实异常仍正常传播；嵌套操作复用保护任务。
2. 主库和插件库统一采用 `CancellationSafeAsyncSession`，保护实际进入驱动的方法，
   包括查询、flush、提交、回滚与关闭；业务取消后仍撤销未提交的事务。
3. 跟踪会话的实际使用者。关闭数据库时拒绝新会话，先取消并等待使用者、归还连接，
   再 dispose。主库关闭同时复位会话工厂，避免重用已关闭的引擎。
4. 引擎初始化取消时回收临时连接池，初始化完成前不发布全局引擎或插件会话工厂。
5. 停机先停止 HTTP、调度器和流循环，再卸载插件、等待托管及未托管任务，最后关闭存储。
   清扫前等待已开始的驱动操作，避免打断 SQLAlchemy 内部派生的 close 任务。
6. 停机期间停止派生日志事件任务，控制台和文件输出继续工作；重新初始化可恢复广播。
7. Mnemosyne 删除独立的事务副本，继承框架统一实现；只读桥接只负责复位 `query_only`。
   预取失败时仅移除仍指向该失败任务的 ID，不删除后续新任务。

数据库驱动操作期间收到取消，可能需要等待现有数据库超时。提交已经开始后收到取消，
提交可能已经生效，不能把 CancelledError 当作“没有写入”的证明。
LLM、网络等业务等待不因此变为不可取消。

## 验证范围

- 主库、指定 CRUD 工厂、插件库、Mnemosyne 实际数据库四个入口。
- 自动提交、手动提交/回滚、重复取消、关闭、flush 约束失败与真实异常传播。
- execute、scalar、scalars、get、flush 五种入口的驱动等待点取消。
- 真实 aiosqlite 工作线程中的阻塞 SQL 被重复取消后，连接归还且能继续查询。
- 数据库关闭与查询并发、关闭方自身取消、旧工厂拒绝新会话、重新初始化。
- 主库与插件库初始化取消后的临时引擎释放。
- 全局任务快照取消及嵌套清理，不使用日志过滤掩盖连接池错误。
- 独立 Python 进程内连续五次真实 Bot.shutdown；每轮检查连接归还、无残留任务及
  SQLite integrity_check，进程退出日志不得出现重置、终止、泄漏或事件循环关闭异常。
  SQLite 和停机方法真实执行，HTTP、MCP、向量库等外部服务使用测试替身。
- 数据库、并发、日志、插件存储、流循环、信号处理和 Mnemosyne 全量插件回归。

原有测试中 Windows URL 分隔符、连接回收时间、全局 TaskManager 入口及插件
版本断言已与现有实现对齐；没有降低连接归还、数据库完整性或宿主加载卸载断言。

## 维护要求

插件使用 `PluginDatabase.session()`，不要再复制事务管理。批量取消任务须使用统一清理
规则，数据库关闭前必须等待实际使用者退出。框架与本次插件修改应一起使用。

2.1.2 通过公开 `storage_api` 使用安全收尾接口，声明要求 `storage_api>=1.1.0`。
旧宿主会在导入插件之前被 API 版本校验拒绝；需要先更新主程序。

本次验证使用临时数据库，未重启生产 Bot，未修改生产配置或记忆数据。
