# Engram Memory

Engram Memory 保存可追溯、可检索、可修订的正式记忆，并根据正式记忆变化更新核心人物印象。

## 工作方式

1. **保存正式记忆**：`memory_write` 创建记忆，`memory_revise` 保留旧版本并记录修订，`memory_invalidate` 作废不再有效的记忆。每条记忆保留人物关联、来源与稳定 ID。
2. **更新人物印象**：正式记忆提交后发布变化事件。Persona 按受影响人物合并任务，依据全部关联正式记忆维护核心人物印象；启动后在后台补建尚未完成新方案生成的人物。
3. **检索与回忆**：`memory_search` 检索正式记忆，`memory_read` 查看当前内容、版本历史和证据。`person_lookup` 默认返回当前人物印象与近期相关记忆，也可显式查询以前的印象。回复前可尝试自然闪回，仍受相关性、耗时预算和冷却条件限制。

### 检索时间

`memory_search` 的 `start_time`、`end_time` 接受 ISO 8601 日期或时间，例如 `2026-01-02`、`2026-01-02T09:00:00+08:00`、`2026-01-02T01:00:00Z`。未带时区时使用既有的 `diary.timezone`，带时区时保留其明确偏移，内部统一转为 UTC；不接受“昨天”等相对时间文本。

纯开始日期从当地零点起，纯结束日期包含当地整日；完整日期时间按指定时刻筛选。时间范围作用于记忆的最近经历时间，缺省为创建时间，不是正文中任意提及的日期。

## 正式记忆结构

- **Memory**：正式记忆的稳定身份、创建时间和当前状态。
- **Revision**：按版本保存正文、记忆类型、主要人物和次要人物；修订历史会保留，可回看旧版本及其来源。
- **Evidence**：记录来源类型，并关联旧记录或已保存的消息副本，用于查证记忆依据。

插件独立数据库保存人物印象的完整版本及成功审查记录；每人的最新完整快照代表插件的当前版本，旧版本保持不变。核心数据库的 `PersonInfo.impression` 保存供框架读取的当前正文，只有与插件最新版的正文、生成方案及最近成功摘要一致才作为可信印象使用。正式记忆仍是人物印象最主要、最可靠的依据；人物印象及其历史都不代替正式记忆或来源证据。

启动时先核对全部非空核心人物印象，包括没有正式记忆关联的人。无法匹配插件当前版本的正文先完整归档为未认证历史，再在核心库写入精确占位文字“（暂无印象）”；已匹配的新稿保留。归档失败时不替换核心正文；归档后重新读取人物，正文已变化就跳过，写入及回读失败会停止插件加载，下次启动可重试。重复启动不会重复归档相同旧稿或将占位文字当成有效印象。

清理完成后，后台补建只扫描 ACTIVE 当前版本关联的主要及次要人物，按核心 ID 去重，不阻塞等待模型。旧稿与占位不进入首次生成底稿。生成与引用校验通过、核心写入并回读一致后才保存插件新版本与成功记录；失败时保持占位，不恢复旧稿。没有 ACTIVE 正式记忆时不首次生成，等待有新的关联记忆再处理；新版印象的全部正式依据撤回时核心写入“（暂无印象）”，插件历史保存空印象版本。

补建、正式更新和重试共用一个队列，默认同时处理最多 3 个人，同一个人物不并行；生成期间到达的新变化合并到后续批次。输入在生成期间变化时丢弃过期结果并重排。一次任务最多尝试 3 次，重试前分别等待 2、4 秒，等待不占处理名额；耗尽后保留错误与待处理变化，后续新变化可再次触发。首次补建失败的人物没有成功标记，下次启动仍会被发现。插件卸载会取消并等待扫描、生成与重试任务。

除全部正式记忆外，请求还提供最近 7 天真实聊天中的连续片段，按时间分布取样；默认最多 500 条，其他参与者和 Bot 的话也计入。片段保留时间、发言者、角色、聊天流、消息与回复 ID，超出配额时明确标记开头截断，不随机拼接单句。聊天只用于谨慎的近期轻量观察，不能推翻正式记忆或凭少数发言推断稳定人格。聊天独有观察不伪配 Memory ID，非空印象整体仍须引用有效正式记忆。可信底稿的后续更新只增删改受影响部分，保留其余有效原文；正常生成不会输入所有历史快照。

### 历史人物印象

每个人独立使用 `revision_no` 从 1 递增，同时记录 UTC 时间、调整原因、生成方案、正文摘要和完整正文（含 Memory 尾注）。归档旧稿的生成方案为 `NULL`，仅供历史查看，不作为成功生成或当前底稿；之后的新稿沿用该人物的版本序列继续追加。正文、引用或生成方案变化时保存下一版；无变化审查、失败和过期结果不制造新版本，旧审查记录不补造缺失的正文。

`person_lookup` 的 `view` 默认是 `current`。使用 `view="history"` 返回按版本倒序排列的目录；再使用 `view="revision", revision_no=1` 读取指定版本。历史结果明确标记为“当时的主观印象”，不能当作当前事实或正式记忆依据。查询本身不调用生成模型，撤回当前依据后仍可显式回看历史。

### 人物印象增量阅读

核心正文与插件当前版本匹配后才可作为底稿。首次审查、底稿为空或已读版本记录未知时，系统会完整读取一次该人物的当前有效记忆版本；已有可信印象正文会作为底稿保留，不会因此强制所有人物在启动时重写。后续按 `revision_id` 区分已读与新增版本：新版本提供完整标题、正文及人物关联信息，已读版本只提供标题、记忆 ID、版本 ID 和人物关联信息。同一记忆 ID 修订后会被视为新版本并再次提供全文。

输入变化前后的当前版本目录会一并提供；已失效的旧版本仅用于识别变化，不作为当前依据。私有 `persona_memory_read` 工具通过 `memory_ids: list[str]` 按需补读一条或多条当前相关记忆，不读取无关或已失效记忆；原有记忆引用 ID 与正文圈号格式保持不变。只有审查成功后才记录已处理的全部当前版本，不按模型输出的引用清单推进。失败、输入过期或任务取消均不推进已读状态；正文未变化时仍记录成功阅读，但不创建虚假的正文历史版本。

每条记忆有一个主要人物，可有关联的次要人物。人物 ID 必须来自核心人物查询，不能用昵称、猜测的账号或自行拼接的标识替代。主要人物是记忆最直接描述的人，不必是来源发送者；被提及但没有亲自发言的人也可以关联，只要身份已核实且正文与来源支持该关联。人物关联不表示本人确认了陈述，也不能把其他人的经历归给此人。

人物印象请求注入完整人设，复用核心 `actor` 模型任务，不设正文字符上限。模型以 `[Memory: UUID]` 引用真实记忆 ID，程序校验依据后，将相邻引用合为正文圈号，完整 ID 放在末尾的“记忆依据”中；相同依据组复用编号，一条尾注可对应多条记忆。圈号覆盖 1 到 50，更多尾注使用 `[51]` 等编号，不限制引用数量。再次更新前，程序将尾注还原为行内引用；已有行内引用格式在印象更新时转换，不批量重写历史印象。可通过 `memory_read` 核对依据；转述、计划和不确定判断保留其证据边界，少量观察不足以证明稳定人格。印象本身不作为记忆证据。

### 聊天中的人物印象

长期记忆与人物印象可自然保留对方明确希望使用的称呼、常用名字和交流偏好，不从账号昵称或一次玩笑推断长期偏好。印象仍以相处形成的感觉为主，不变成人物档案或事件清单。

群聊通过常驻指引和工具描述要求模型：跟某个人开始聊天，或有人新参与时，先调用 `person_lookup` 的当前视图读取其印象，再回应；同一段对话已经读过的印象不必每句话重复查询。这是模型行为要求，不是程序强制的回复拦截。

私聊默认按聊天流的准确核心人物 ID 读取对端已认证的当前印象，以流私有的 `FIXED + FOREVER` SystemReminder 注入首个 User，不要求模型开始聊天前再调用工具。首轮无需预载事件也可注入；后续印象改变时替换同名旧块，不保留多份稿件。不存在可信当前印象时移除旧提醒，不回退旧残留或触发模型生成。没有聊天流、未使用记忆提醒或日记与印象内部生成请求不注入。

可在项目根目录运行不连接数据库或模型的离线示例：

```powershell
uv run --no-sync python -B -m plugins.engram_memory.examples.private_persona
```

## 写入与来源

写入前先通过 `memory_search` 检索同一人物、主题或经历，再回读已有正文，避免重复。新发生的独立事实创建新记忆；对已有记录的纠正或补充创建修订，不覆盖旧版本。正文由 Bot 根据来源组织为完整、自然的叙述，区分转述者、原陈述者、计划与实际发生的事实，不把猜测改写成确定结论。

| Action | 参数 |
| --- | --- |
| `memory_write` | payload 必填 `content`、`memory_kind`、`primary_person_id`、`source_message_ids`；可选 `secondary_person_ids`。 |
| `memory_revise` | payload 必填 `memory_id`、`based_on_revision_id`、`content`、`primary_person_id`、`source_message_ids`；可选 `secondary_person_ids`、`memory_kind`、`reason`。版本 ID 使用 `memory_read` 回读的当前版本。 |
| `memory_invalidate` | `memory_id`、`reason`、`source_message_ids`；作废保留历史版本与证据。 |

`source_message_ids` 选择当前聊天中直接支持正文的真实消息 ID，并包含理解回复、问答或指代所需的来源；按接口返回的来源目录核对，不能猜测或伪造。只有实际引用的消息保存为证据快照，来源聊天、消息身份、原文和消息时间由程序记录。“帮我记住”的指令不能替代具体事实的来源。历史导入记忆保留原记录及来源类型，不补造未保存的消息。

## 管理页

插件加载后提供只读管理页 `/engram-memory`，包含概览、正式记忆和人物印象三个页面。管理数据 API 只接受回环地址请求，浏览页面不会生成印象或修改记忆。图标资源随插件打包，不依赖外部 CDN；上游许可见 [router/lucide.LICENSE](router/lucide.LICENSE)。

正式记忆和人物均在服务端筛选、计数和分页，每页可选 20、50、100 条，也可直接跳转页码。记忆可按状态筛选，并搜索标题、正文或完整 ID；人物可按平台账号、内部 ID、平台昵称、群名片或印象正文搜索，并按最近资料更新或昵称排序。搜索中的百分号和下划线按普通字符匹配，不作为通配符。详情跳转保留原列表的搜索、筛选、页码和滚动位置；手机端在列表与详情之间切换。

列表以标题、人物名称和正文摘要为主。记忆详情先显示当前正文，历史版本、来源和标识信息分区折叠；来源区区分已保存、缺失和隐私删除的消息快照。完整记忆、版本、人物和来源 ID 保留在标识信息中，可逐项复制。人物印象正文显示原圈号，依据显示记忆标题并可打开对应记忆；不存在的依据明确标为不可用。复制完整印象保留全部原始标识，不修改存储正文。

人物档案分别展示平台昵称、最近记录的群名片和平台账号，标题优先使用平台昵称。最近群名片是核心人物记录的全局字段，不代表指定群的当前名片。资料更新时间与印象保存时间分别显示；只有当前完整印象匹配插件历史快照时才显示保存时间，没有对应记录时显示时间未记录，不用资料更新时间替代。

Doctor 提供正式记忆、版本证据、检索入口和向量索引的检查与派生修复。历史候选独享的消息证据不纳入正式版本的快照完整性检查；修复不删除正式记忆、旧候选、整理会话或来源数据。

## 配置与数据

插件默认启用。可在插件配置中调整以下 vNext 项：

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `vnext.persona.recent_memory_limit` | `10` | 人物查询返回的近期记忆条数 |
| `vnext.persona.max_concurrency` | `3` | 补建、正式更新和重试共用的最大人物并发 |
| `vnext.persona.recent_chat_days` | `7` | 辅助聊天的最近天数 |
| `vnext.persona.recent_chat_max_messages` | `500` | 辅助聊天总消息上限，包含全部发言者 |
| `vnext.retrieval.default_limit` | `5` | 默认检索返回条数 |
| `vnext.retrieval.max_limit` | `20` | 检索返回条数上限 |
| `vnext.retrieval.rrf_k` | `60` | 多路召回的排名融合参数 |
| `vnext.prompt_injection.reminder_at_end` | `true` | 将记忆使用指引动态放在最新一轮输入；关闭后固定在首轮输入 |
| `vnext.flashback.enabled` | `true` | 开启自然闪回 |
| `vnext.flashback.trigger_probability` | `0.25` | 每轮回复尝试闪回的概率；`0` 关闭，`1` 每轮尝试 |
| `vnext.flashback.context_turns` | `6` | 闪回检索使用的上下文轮数 |
| `vnext.flashback.latency_budget_ms` | `1200` | 闪回检索的耗时预算，单位毫秒 |
| `vnext.flashback.max_memories` | `2` | 每轮闪回最多注入条数，可设为 `0`、`1`、`2` |
| `vnext.flashback.cooldown_turns` | `3` | 同一记忆在同一聊天中的重复闪回间隔 |
| `vnext.vector.worker_retry_limit` | `3` | 向量任务的失败重试上限 |

正式记忆数据库默认位于 `data/engram_memory/vnext.db`，向量索引默认位于 `data/engram_memory/chroma`。可通过 `storage.vnext_db_path` 和 `storage.vector_db_path` 调整位置。

启用后，插件注册三个正式记忆 Action、三个查询 Tool、记忆变化、闪回、私聊印象与聊天日记 EventHandler、记忆 Service、Doctor 与管理 Router，并维护派生向量索引。配置的 vnext 节仅包含 `persona`、`retrieval`、`flashback`、`prompt_injection`、`vector`；独立聊天日记使用 `diary` 节。自然闪回可通过 `vnext.flashback.enabled` 关闭。

记忆使用指引和闪回通过框架原生 `SystemReminder` 注入，不修改模型权重。指引默认随最新输入刷新；闪回按记忆 ID 管理，同一记忆不会反复累加。正式记忆更正或作废时，已有提醒随之更新或移除；来源隐私删除也会撤回对应提醒。提醒源在插件卸载时清理，不保证跨 Bot 重启保留；正式记忆库不受影响。未触发闪回时不调用向量模型，触发后仍受相关性、冷却和耗时预算限制。

正式记忆变更产生的向量待投递项由后台任务处理，轮询间隔为 10 秒；记忆变化事件的发布不直接更新向量索引。达到失败重试上限后停止自动重试，需明确执行恢复操作，避免无休止消耗模型额度。

正式记忆、历史版本、来源证据、数据库中的候选与整理会话记录、导入资料和现有备份均保留。这些数据独立于运行配置保存。配置加载只过滤本地遗留的废弃字段，不重写配置文件，其他未知字段仍接受严格校验。

## 独立聊天日记

聊天日记为每个群聊或私聊流按自然日保存一份完整正文，只记录当前采集许可允许的真实聊天。群聊与私聊分别配置开关，默认均开启；触发模式为 `time`（仅时间）、`messages`（仅消息数）、`either`（任一条件满足）或 `both`（两项都满足）。默认群聊使用 `both`，成功整理后间隔 10800 秒且至少有 200 条未处理消息；私聊使用 `messages`，阈值为 100 条。

首次初始化每条流时从最近 `context_days` 个自然日回填，默认七天且包含今天；缺少消息的日期不补空日记。后续处理固定本轮消息截止位置，并按消息所属时区日期分批，因此跨午夜的批次分别归入对应日期。每次生成都以目标日期已有正文为底稿，替换该日完整内容；日记正文提交与处理游标推进在同一事务中，生成或提交失败时保留原正文和原游标。旧日记不会因超过七日而删除；该天数只限制注入窗口。

整理前后都会通过已有公开配置接口只读核对当前消息采集许可。当前支持 QQ 流的 SnowLuma 群聊、私聊名单与禁用用户策略，不导入或修改适配器实现；其他平台、配置未加载或许可撤回时不回填或提交。模型请求使用 `actor` 任务和独立的新请求，只携带完整人设及目标日期、时区、聊天类型、当天旧正文、少量前文和本批新消息，不复用正式记忆的提醒、工具历史或会话记录。日记只供近期交流回顾使用，不写入或修改正式 Memory 与 persona。

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `diary.group.enabled` / `diary.private.enabled` | `true` / `true` | 分别开启群聊与私聊日记 |
| `diary.group.trigger_mode` / `diary.private.trigger_mode` | `both` / `messages` | 时间、消息数、任一或两者同时满足 |
| `diary.group.interval_seconds` / `diary.private.interval_seconds` | `10800` / `10800` | 时间条件的间隔秒数 |
| `diary.group.message_threshold` / `diary.private.message_threshold` | `200` / `100` | 消息数条件的未处理消息阈值 |
| `diary.group.context_days` / `diary.private.context_days` | `7` / `7` | 含今天的注入自然日窗口 |
| `diary.max_concurrency` | `3` | 跨聊天流的后台并发上限，同流串行 |
| `diary.batch_messages` / `diary.context_messages` | `100` / `6` | 连续新消息批大小与额外前文条数 |
| `diary.retry_limit` | `2` | 首次失败后的额外重试次数 |

没有新消息时所有触发模式均跳过。后台按最旧未处理消息连续推进，成功消息 ID 作为重启续读锚点；锚点不再存在时停止推进并报告错误，不跳过未知缺口。首次回填不等待正常触发阈值，之后按各类触发条件整理。生成期间到达的新消息留到下一轮。

回复时只注入当前流最近自然日窗口内的非空日记，不附加尚未归档的原消息；窗口内没有日记时不注入，并移除请求及流提醒中的旧日记块。日记使用动态 SystemReminder，每次剥离历史中的旧块，只在最新一条 User 中保留一份当前日记，正常聊天消息不受影响。

`diary.database_path` 是独立 SQLite 数据库路径，使用相对路径时相对于应用工作目录；`diary.timezone` 决定自然日边界。时区数据库依赖 `tzdata`，部署环境需要提供该依赖。

可在项目根目录运行本地隔离示例：

```powershell
uv run --no-sync python -m plugins.engram_memory.examples.chat_diary
```

## 迁移已有 Engram 数据结构

当前 Schema 为 v5，将当前人物印象保存在核心数据库，并在成功审查中记录生成方案、已读版本及历史快照。升级插件后正常启动即可：初始化会自动将已知的 Schema v1、v2、v3、v4 升级至当前版本，无须手动运行脚本或切换数据库路径。迁移在运行时数据库打开、后台任务启动前完成；已经是当前版本时不重复迁移，也不创建升级备份。

自动迁移先锁定写入，并用 SQLite Backup API 保存包含已提交 WAL 数据的一致快照。备份保存在数据库同级的 `backups/` 目录，文件名包含旧 Schema 版本及唯一标识。随后在同一个 SQLite 事务内完成结构转换和版本更新，检查完整性及外键后提交。备份失败或迁移失败会停止插件加载；未提交的结构和版本更新会回滚，下一次启动仍可重试，不把半升级的数据库交给后台任务。未知版本、缺少版本记录或比当前代码更新的数据库明确拒绝，不猜测结构、不自动降级。进程退出后未提交事务由 SQLite 恢复；备份不替代正常的数据备份策略，不能保证磁盘故障或硬件损坏时绝对无损。

v4 只增加 nullable `seen_revision_ids` JSON 列；v2/v3 同时补入既有的三个审查字段，原有行和历史资料不变。v1 使用共享转换规则重建插件表，将退役字段与派生记录归档在旧库备份旁，同时保存迁移报告。正式记忆及历史正文保留；历史审查中缺失的新字段填为 `NULL`，不伪造已读状态或人物印象认证，不读取或覆盖核心人物印象。v1 的检索派生文本变化通过既有向量 Outbox 处理，不调用迁移模型；v2/v3/v4 不改写检索入口或向量目录。备份、归档和报告可能包含私人资料，仅供本机恢复与核对，不应对外分享。

离线副本迁移脚本仅用于维护或预演，不是正常升级的必需步骤。输入须是已经合并 WAL、没有 WAL/SHM 文件的独立快照，不能只复制主文件而遗漏尚未合入的数据。从项目根目录运行：

```powershell
uv run --no-sync python plugins/engram_memory/scripts/migrate_schema.py --source data/memory-copy/vnext.db --target data/memory-migrated/vnext.db
```

脚本要求交互确认，拒绝当前配置正在使用的数据库和已存在的输出文件。它与自动迁移复用转换规则，只写新副本，并核对来源未变、原始字段摘要、数据库完整性及外键。离线维护时，向量目录应另行复制并与新数据库一起切换；脚本不会操作 Bot、修改配置或切换生产库。

## 从 Booku 迁移记忆

迁移器只把 Booku 的 `memory` bucket 导入 Engram；`knowledge` 文档片段会明确计数并跳过，不会变成正式记忆。迁移不会写入当前 Engram 或 Booku 数据库，也不会修改配置。目标目录必须是新目录，已存在时拒绝覆盖。

在项目根目录运行：

```powershell
uv run --no-sync plugins/engram_memory/scripts/migrate_booku.py
```

默认先显示 Booku 配置所指元数据库中的记忆数量，并说明知识片段将被跳过。只有在提示处准确输入 `迁移`，才会创建新目标目录并执行导入、重建向量索引、回读和实际检索核对；其他输入不会开始迁移。`--preview` 只检查并显示预览后退出。没有 `--apply` 或 `--yes` 这类跳过交互确认的选项。

可选参数：

| 参数 | 行为 |
| --- | --- |
| `--source` | 指定 Booku SQLite 元数据库的相对路径；省略时读取 Booku 配置中的路径。 |
| `--output` | 指定全新的相对输出目录；默认 `data/engram_memory/booku-import`。 |
| `--batch-size` | 每次向量模型请求的记忆条数；默认 `32`，上限 `100`。 |
| `--resume` | 仅续跑本迁移器已完整导入、但向量索引失败的私有输出目录；仍需交互输入 `继续`。 |

每条旧记忆成为一条正式记忆及其初始版本，保留原记录创建时间；Booku 没有保存的旧版本不会补造。已软删除的记录写为 `TOMBSTONED`，归档记忆仍可使用。临时备忘不导入为正式记忆，只留在源库快照中。缺失、异常或占位的人物标识不会靠昵称推测；旧来源只记为 `LEGACY_RECORD`，不会伪造消息证据。

类型映射为 `event → EVENT`、`preference → PREFERENCE`，其余旧记忆类型进入 `FACT`；旧分类、标签和原始字段完整留在来源记录中。筛选依据是 `bucket`：记忆区中原类型为 `knowledge` 的记录仍是记忆，会保留；知识库 `bucket=knowledge` 的文档片段不会导入。迁移不让模型改写旧正文。

完成后，新目录包含 `vnext.db`、`chroma`、Booku SQLite 原始副本，以及供本机核对的简明 `report` 和 `events`。原始副本是完整 SQLite 快照，包含源库中的所有内容。迁移输出可能含私人资料或凭据，仅供本机核对，请勿对外分享。迁移本身不切换正在运行的 Engram。需要启用新库时，先停止 Bot，再手动将 `storage.vnext_db_path` 与 `storage.vector_db_path` 成对改到新目录；不会自动合并或覆盖现有 Engram 记忆，本说明中的迁移步骤也不会替你切换配置。
